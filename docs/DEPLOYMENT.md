# Deployment preparation

Local Compose is a development topology. `artisan serve`, local Mailpit, debug settings, and debug APK signing are not production deployment choices.

Before deployment build a PHP 8.4 FPM or equivalent supported application-server image from the locked backend, run behind a TLS reverse proxy, serve only backend/public, disable APP_DEBUG, set APP_ENV=production and HTTPS APP_URL, configure trusted proxies explicitly, enforce secure HttpOnly SameSite session cookies, restrict CORS to intended clients, and prohibit public access to private storage. A separately supervised queue worker must run php artisan queue:work --tries=3 --timeout=60. Schedule token pruning and production maintenance; alert on failed jobs and lag. Configure real mail, private evidence storage, Google keys/restrictions/quotas and Firebase before claiming these integrations work.

Run composer install --no-dev --prefer-dist with the lockfile, npm ci && npm run build in the frontend build stage, migrations with backups and a controlled rollout, and Laravel configuration/route/view caching. Do not run local account fixture generation or fake-incident seeds in production. Seed only reviewed agency/category configuration. Generate the application key once and retain it securely. Grant MySQL least-privilege database access and require authenticated encrypted remote transport.

Publish Android using a securely managed release signing key, a real HTTPS API URL, restricted Maps configuration, reviewed privacy notices and foreground location permissions. Never embed MySQL access in the APK. Test on physical devices for stale GPS, approximate location, denied permissions, interruptions, notification permission denial, accessibility and screen-reader confirmation.

The current task validates local development only. A production FPM image, deployment automation, backups/restores and signed release deployment are not yet built or tested. This document records prerequisites rather than asserting production readiness.


## Laravel Cloud: Firebase messaging secret

Attach a production secret named `FCM_SERVICE_ACCOUNT_JSON` whose value is the complete, unmodified Firebase Admin service-account JSON (including the outer braces). Preserve JSON escaping in the private key; do not wrap the entire value in extra quotes, base64-encode it, or upload it to a public bucket. Set `FCM_ENABLED=true` and `FCM_PROJECT_ID=cdrmapp` for this deployment. The Android `google-services.json` is a separate client configuration and cannot be used here.

Deploy the backend revision that supports this secret, rebuild cached configuration if managed manually (`php artisan config:cache`), and ensure the secret is available to the queue-worker process as well as the web application. Restart long-running workers after a deployment or secret change. If no managed worker exists, configure one to run `php artisan queue:work --tries=3 --timeout=60`. No database migration or APK rebuild is required for this backend configuration change.

The JSON secret takes precedence over `FCM_SERVICE_ACCOUNT_FILE`; an invalid nonempty secret fails rather than silently using an older file. Leave the file variable unset when using the secret. `FCM_SERVICE_ACCOUNT_FILE_HOST` only belongs to the local Docker overlay. Existing file-based deployments remain supported. Credential changes use a fresh OAuth token cache key. Keep cached Laravel configuration private because it contains the credential.

Enable Firebase Cloud Messaging API (HTTP v1) in the Google Cloud project and grant the service account permission to send messages. To verify delivery, sign in on a physical Android device, enable notifications, and change the status of an authorized report belonging to that account. Inspect queue failures and Laravel Cloud logs if delivery fails; never share private keys, OAuth tokens or device tokens. Local automated checks use generated credentials and mocked Google responses; they do not verify live production delivery.

Report updates now send a generic visible FCM notification plus status data at high Android priority on channel `incident-status`. The notification contains no report description or location and uses private lock-screen visibility. Recipients without a registered device are skipped before requesting an OAuth token. Deploy this backend change and rebuild/install the Android APK together to include the notification icon, pre-created channel and device-registration retry feedback. An accepted FCM request is not proof that Android displayed a notification: app/channel permissions, connectivity and force-stop state still apply.

History refreshes when the Android History tab opens or resumes and polls every 15 seconds while visible, independently of push delivery. The manual Refresh status action remains available. Foreground History refresh does not register a device repeatedly. Firebase token/registration failures appear with a Retry notifications button; debug builds log only failure classes under `CDRMAPP_PUSH`. If no notification arrives, check `php artisan queue:failed`, confirm the queue worker uses the production secret and the configured queue connection, and confirm the signed-in user has a registered device. Do not enable `APP_DEBUG` or paste credentials/device tokens into support logs. Synthetic reports marked `is_test=true` intentionally do not notify anyone; use an explicitly labeled test submitted through the citizen app when testing delivery with authorized staff.

## Laravel Cloud: persistent CMS image uploads

Announcement, service, and team images can use a private Laravel Cloud Object Storage bucket. The application records the disk alongside each image and returns a 30-minute signed `image_url` in public content responses. Reload the page or fetch the API again after a link expires; do not cache content responses or rendered HTML beyond this lifetime. Only published content is returned by public endpoints. Treat signed links as bearer links: someone who receives a link can use it until it expires, even if the item is subsequently unpublished.

1. Deploy the code containing the S3 adapter and image-disk migration. Keep `php artisan migrate --force` in the deployment commands.
2. Open the application's **production environment** in Laravel Cloud. On its infrastructure canvas, choose **Add bucket**, then create **Laravel Object Storage**. Review the displayed storage costs before creating it.
3. Use a name such as `cdrmapp-media`, disk name **private**, and **Private** file visibility. Choose Automatic jurisdiction and an Asia-Pacific location hint for the Singapore app region if those choices are available. Attach it to the production environment with read/write access and make it the default disk so Cloud injects its connection settings.
4. In the environment's custom variables, set `CMS_MEDIA_DISK=private` (or the exact disk name shown on your attached bucket). Laravel Cloud supplies the attached bucket's connection settings; do not paste credentials into source control or chat. Remove conflicting manually entered AWS connection variables if they would override Cloud's bucket settings. The app supports `AWS_ENDPOINT` / `AWS_ENDPOINT_URL` and `AWS_DEFAULT_REGION` / `AWS_REGION`. You do not need `AWS_URL` for this private bucket. Do not set public object visibility or ACLs: Cloudflare R2 uses bucket-level visibility.
5. Redeploy after attaching the bucket and saving variables. Make sure the migration succeeded. If managing config caching manually, rebuild it after the variables are applied (`php artisan config:cache`).
6. Edit the announcement in Admin, select the image again, and save. Open `/pages/announcements` in a private browser window. The image request should return HTTP 200 from the bucket with a signed URL, not `/storage/...`. Redeploy once more and confirm that a fresh page still displays it.

Old uploads retain their original `public` disk location; setting `CMS_MEDIA_DISK` does not move them. If they still exist, back them up before redeploying and re-upload through Admin. Missing files on ephemeral servers cannot be recovered by this change. `storage:link` is only needed for local/public disk images and does not provide persistent cloud storage.

If saving an announcement produces no visible result, check the Admin status above the form. It now reports required-field validation, saving, uploading, and upload failures separately. A successful image upload reports **Content and image saved successfully.** The record card shows the saved image or **No image attached.** A timeout does not prove that the server stopped processing: refresh and check the saved image before retrying. If a saved image fails to load, inspect its image request's HTTP status; if no image is attached, inspect the POST request ending in `/image`. Share only status codes and error messages, not credentials, cookies, or signed URLs. The isolated browser regression check is `node infra/cms-media-smoke.cjs`; it intercepts HTTP requests and does not connect to a real bucket.

CMS images use the configuration above. Profile photos support a private persistent disk as described below. Incident evidence still explicitly uses the private **local** disk and needs a separate persistent private-storage implementation before relying on its durability in production. Never place evidence in a public bucket.

The tests validate disk selection, replacement, failed writes, publication filtering, page/API URLs, and the real S3 adapter's URL signing locally. A live Laravel Cloud bucket is not provisioned or verified by these tests.

Reference: [Laravel Cloud Object Storage](https://cloud.laravel.com/docs/resources/object-storage).

## Laravel Cloud: profile photos and signed-in avatars

Deploy the updated backend and rebuilt web assets with `php artisan migrate --force`. Migration `2026_10_29_000001_add_profile_photo_disk_to_users` adds the nullable disk field that keeps each saved photo tied to its storage location. When the existing Cloud configuration has `CMS_MEDIA_DISK=private`, new profile photos automatically use that same private disk. Otherwise they default to local storage; set `PROFILE_MEDIA_DISK` to an attached private persistent disk for production. This must be a private bucket, with no per-object public ACL or public image URL.

Photos are served only through the authenticated account's `/api/v1/me/photo` endpoint, with private/no-store headers and a new URL version for each successful replacement. The current user's sidebar avatar and profile preview update immediately after upload and display the saved image on later visits. A missing photo falls back to the user's initial. Failed writes retain the previous photo; successful replacements remove the old object from its recorded disk. Existing records without a disk keep using local storage until the user uploads a replacement. Files already lost from an ephemeral deployment cannot be recovered; re-upload them after deploying this revision. No Android rebuild is required.

Validation: `ProfilePhotoTest` covers admin/officer uploads, stored-disk replacement, account isolation, private reads and failed storage/database writes. `node infra/profile-photo-smoke.cjs` uses intercepted requests to check both avatars, reloads, cache-version changes, upload failures/retries and fallback images without connecting to a live bucket.


## Simplified reports and module removal deployment

New incident submissions are restricted to the San Jose del Monte polygon bundled in `backend/resources/geo/san-jose-del-monte.geojson`; provenance and ODbL attribution are documented alongside it. The server rejects both GPS and manually pinned locations outside this shape with HTTP 422 and `error.fields.location`. No report, audit/status history or notification is created for a rejected submission. Locations exactly on the boundary count as covered. Existing reports and idempotent receipts remain accessible, including reports received before this restriction.

Deploy this backend validation and rebuild/install the Android APK to show the coverage message instead of the generic validation error. A definite coverage rejection clears only that report's unconfirmed retry record so its actual location can be corrected; the form retains the report details. Network uncertainty and other validation errors still retain the exact retry payload. Do not move a pin to an incorrect location to pass validation. For incidents outside SJDM, use the appropriate local emergency services. No database migration or new environment variable is required.

Marking a report Done now requires `note` (nonblank, at most 2,000 characters) on `PATCH /api/v1/incidents/{id}/status`. Both watchlist and map/detail actions open a response-note form before submitting. Status change, response log, status history and audit note are saved in one transaction; a failed response write leaves the report unchanged. Repeating a successful Done request does not create another response. Mark as undone preserves all previous notes; completing it again adds a new entry. Existing notes and assignments are preserved. The report detail shows a read-only Response log with author and timestamp instead of separate Log response and assignment/rerouting forms. Deploy the backend and rebuilt web assets together; no migration or Android rebuild is needed. Old already-completed reports are not given fabricated response notes.

Report generation is administrator-only: `/api/v1/reports` and `/api/v1/reports/export` require the active admin permission. CSV export and the application's print control are shown only to administrators on the dashboard and incident map. Fire, Police and MDRRMO officers retain their agency-scoped `/api/v1/incidents` access, operational dashboard/map, and authorized response/status actions. Deploy backend code and rebuilt web assets together; this permission change requires no migration or Android rebuild.

Deploy the updated PHP code and frontend build together. No new database migration is required for this revision. Reports show Done/Need action, with reversible Mark as done/Mark as undone actions. Legacy resolved, closed, rejected and duplicate rows read as Done; other legacy states read as Need action. Historical rows/status history are not bulk-rewritten. CSV now includes status labels and location/coordinates.

Use **Incident dashboard** (`/dashboard`) for reports and **Map & heatmap** (`/incident-map`) for the separate map. Filters are shared and carried across when switching pages. Dispatch Rules and Infographics management/API/public routes are removed. New reports route directly to their category's active agency, ignoring old dispatch settings. Old rule and infographic data remains stored for history/rollback. The public homepage now displays announcements.

Existing audit entries remain available; new changes include actor/subject and before/after details. Forms clear only after complete successful saves; failed image uploads retain the saved item's ID for retry.

## San Jose del Monte test reports

After deploying, run this in Laravel Cloud production's **Commands** when you want the synthetic demonstration batch:

```bash
php artisan cdrmapp:seed-test-reports
```

It creates exactly five Fire Department (BFP), five Crime / Police Department (PNP), and five MDRRMO reports. Re-running keeps the same fifteen reports without changing their coordinates or workflow state. All are visibly labeled TEST and marked `is_test=true`, so they appear in authorized report lists and map pins but are excluded from both heatmap modes. No email or push notifications are sent. The synthetic reporter is an inactive citizen account at a reserved `.invalid` address; no usable login credentials are produced. Active agencies and linked incident categories must already exist; the command does not modify routing settings or real accounts/reports.

Locations use randomized offsets within fifteen separate cells in the central San Jose del Monte area. Cell corners were checked against the [OpenStreetMap San Jose del Monte administrative boundary](https://www.openstreetmap.org/relation/15662634) (© OpenStreetMap contributors); addresses and events are synthetic and do not identify actual emergencies. The separate map page’s legend and pins use red flame (BFP), blue police badge (PNP), and purple rescue cross (MDRRMO). Done reports use gray versions of the same agency symbols; Mark as undone restores the agency color. Reports awaiting triage remain in the report table but do not have map pins. Pins show the current report page and respect its filters. Clear filters, return to page one, and enable **Show incident pins** to inspect the batch.

Checks: `node infra/map-pins-smoke.cjs` intercepts Google Maps and API requests to validate agency/icon mapping, test labels, positions and anchors without real Maps quota. Backend tests validate counts, repeatability, preservation of existing data, heatmap exclusion, and absence of notifications.


## Password update logout

After deploying this revision, successful profile password changes return the browser to `/login` with a sign-in message, including native form submission when JavaScript is unavailable. Email-link resets also end the browser session and redirect to Login. All roles use the same backend flow. Mobile tokens and remember-me tokens are revoked; when `SESSION_DRIVER=database` (the production default), all database sessions for the updated account are removed without changing other accounts' sessions. The current browser session is invalidated and its CSRF token regenerated. Failed validation/reset tokens do not sign the user out or revoke valid sessions. Android already clears its local authentication state after a successful password change; API responses include the relative Login redirect for web clients. No schema migration or new environment variable is required.

Validation uses `PasswordLogoutTest` for all three roles, both password flows, database-session isolation and token revocation. `node infra/password-logout-smoke.cjs` checks browser navigation and failed-update behavior with intercepted HTTP and synthetic credentials.
